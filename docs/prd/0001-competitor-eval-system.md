# PRD: Competitor Evaluation System (Phase A — Capability Benchmark)

> Status: v1 (post-grilling, 2026-06-22). Supersedes the pre-grilling draft (archived as `*.draft-pre-grilling.md.bak`).
> To be published as a GitHub issue with label `ready-for-agent` once the repo + `gh` are set up.

## Problem Statement

As the Vio PM, I have no continuous, trustworthy signal on how Vio compares to competitor agents on the tasks our users actually care about. Competitor awareness today is ad-hoc and shaped by my own confirmation bias. There is no reproducible way to answer "where is Vio behind, by how much, and is that gap shrinking or growing?" — so roadmap decisions about what to borrow or prioritize rest on gut feel.

A complication discovered during research: **Vio is a local hardware agent** (HDMI + USB-HID box, on-device vision, operates any closed-source app with no API). Most "competitors" are cloud-VM or browser agents on a *different physical layer*. A naive head-to-head on generic knowledge-work tasks would systematically over-credit cloud competitors and under-credit Vio's real moat.

## Solution

A reproducible benchmark that, on a competitor- or Vio-version event, runs a fixed-plus-rolling task suite against Vio and selected competitors; verifies results by **layered artifact/end-state checking** (not transcript reading); calibrates AI scoring against a **human-anchored golden set**; and tracks the **trend of the gap** (the derivative), not a single snapshot. Borrowable competitor features flow out to the Vio roadmap through a two-lane human-gated filter; Vio bugs found during runs are logged lightweight and handed to Vio's existing tracker. Phase A is human-validated on a minimal slice before any automation.

## User Stories

1. As the Vio PM, I want benchmark tasks generated by an independent AI constrained by a "scenario constitution", so the task set is de-biased yet anchored to Vio's real user scenarios.
2. As the Vio PM, I want to own the scenario *mix* while the AI generates concrete task wording, so representativeness is mine and diversity is the AI's.
3. As the Vio PM, I want the task-generating model to differ from every competitor and reviewer model family, so affinity bias is avoided.
4. As an evaluator, I want every run to capture an "no-API operability" axis, so a competitor failing for lack of an API is recorded as a different track, not a Vio capability win.
5. As an evaluator, I want results verified by objective assertions on the artifact/end-state first, and AI review only for genuinely subjective dimensions, so scoring fits a desktop agent instead of mis-applying transcript grading.
6. As an evaluator, I want short tasks run N times for mean+variance, and long tasks scored by few-runs + checkpoints, so non-determinism is measured without exploding cost.
7. As an evaluator, I want every run to record environment metadata (model version, date, params, prompt template), so score changes stay explainable when cloud products silently change.
8. As an evaluator, I want subjective scores produced by a dual-AI panel (Gemini + Codex) against a frozen rubric, calibrated against a human golden set via Cohen's kappa, so the reviewers themselves are validated before I trust them.
9. As an evaluator, I want disagreement between the two panel reviewers auto-surfaced, so disagreement becomes signal (ambiguous task or subtle real gap).
10. As the Vio PM, I want the benchmark as a repeatable time series re-run at version events, so I track the direction and speed of the gap, not a snapshot.
11. As the Vio PM, I want a stable core task layer (~70%) and a rolling frontier layer (~30%), so I keep comparability while probing the gap frontier.
12. As the Vio PM, I want evaluation triggered by release events (competitor or Vio), so effort tracks actual change and intel feeds re-tests.
13. As the Vio PM, I want competitors selected as a mix of same-layer + voice-of-market + a reproducible technical benchmark, with cross-layer comparisons explicitly tagged, so reports are neither unfair nor distorted.
14. As the Vio PM, I want borrowable findings routed through a two-lane filter (user-visible features default-reject on differentiation fit; engineering techniques default-accept on ROI) with a mandatory human gate before any auto-development, so the loop never degrades Vio into a competitor clone.
15. As the Vio PM, I want Vio bugs found during runs logged lightweight (symptom + repro + triggering task) and handed to Vio's existing tracker, so bugs are a by-product not a competing workstream.
16. As the Vio PM, I want a trend board showing gap-over-time per capability domain, so I make roadmap calls from evidence.
17. As the Vio PM, I want to validate the whole loop manually on a minimal slice (1 domain x 5 tasks x 3 competitors x 3 runs) before automating, so I don't harden a broken methodology into code.
18. As the Vio team, I want the long-term option to run this system using Vio itself, so it doubles as dogfooding and a marketing artifact.

## Implementation Decisions

**Modules (the four architectural seams):**

- **Task-Generation module** — an independent task-generating AI bound by the scenario constitution (PM-defined domains + mix). Produces a versioned task bank: stable core layer (~70%) + rolling frontier layer (~30%). The generating model MUST be a different family from all competitors and all reviewers. Every task carries a **"no-API operability" axis**.
- **Execution module** — short tasks run N times (mean+variance); long tasks use few-runs + checkpoint scoring. Emits artifacts, end-state, key screenshots, trimmed transcript, and environment metadata (model version, date, params, prompt template). Competitor environments are selected for "runnable in a controlled desktop environment" first, not "API is easiest" — because the realest competitors (computer-use class) are the hardest to reproduce.
- **Review module (the trust-gate seam — keep it single):** two layers.
  - *Objective layer (first):* programmatic assertions on artifact + end-state — open the .xlsx and check cells/formulas, check .pptx structure, verify desktop automation by end-state. No AI here — this layer wants assertions.
  - *Subjective layer (only what assertions can't judge):* a dual-AI panel (Gemini + Codex) scores **artifact + key screenshots + trimmed transcript**, never the raw transcript, against a frozen rubric. Reviewer disagreement beyond threshold auto-surfaces for human inspection.
- **Sink module** — converts scores into a trend board tracking the gap derivative per domain over version events. Two exits: borrowable-feature -> roadmap (two-lane, see below); Vio-bug -> Vio's existing tracker (lightweight record only).

**Golden set / ground truth (calibrates the panel):**
- The panel (AI) and the golden set (truth anchor) MUST NOT be the same population. The golden set is **human-anchored**: AI proposes scores + rationale + disagreement flags, but the score recorded is the one the PM approves (Lane A — AI proposes, human disposes). AI may propose, never vote as a peer — else kappa is AI looking in a mirror.
- Rubric: roll-and-freeze — trial-score 5 samples, freeze rubric, then score 20-30.
- Golden set is versioned with the scenario constitution; reviewed at version events; stale samples retired. Blind scoring where feasible (hide which artifact is Vio's).

**Borrowable-feature -> roadmap (two-lane, human-gated):**
- Carrier: one GitHub issue per borrowable point, 3 columns: `what the competitor does | value hypothesis for Vio | differentiation fit (high/med/low/conflict)`.
- *Lane 1 user-visible features:* filter on differentiation fit; **default REJECT**, only "high" passes the human gate (copying cloud-general features dilutes the "be the Mac" moat).
- *Lane 2 engineering/efficiency techniques* (token savings, latency, retry robustness): filter on ROI; **default ACCEPT** unless too costly.
- Long-term closed loop: eval -> board -> AI auto-prioritizes -> **human gate (`ready-for-human`)** -> AI auto-development. The human gate is mandatory and non-removable.

**Cross-cutting:**
- **Trend over snapshot** — re-run the fixed core layer at every version event; the primary output is gap change, not absolute score.
- **Event-driven, not calendar-driven** — re-tests triggered by competitor/Vio releases; this is where intel-tracking (workstream C) connects into evaluation A.
- **Isolation** — cloud/API competitors need credential isolation only; locally-installed competitors need environment isolation (containers preferred; VM / dedicated machine when GUI/full-OS needed) — never the PM's working machine. Promoted from Phase 2 to a Phase A prerequisite because same-layer competitors can't run headless.
- **Human-first, then automate** — prove the methodology by hand on the minimal slice before hardening into code.

## Testing Decisions

- A good test asserts external behavior of the methodology, not its internals: e.g. "same artifact scored twice by the panel yields scores within tolerance", not "the reviewer prompt contains string X".
- **Primary validation = the Review seam.** Build the human-anchored golden set (20-30 samples), measure panel-vs-human agreement (kappa). Below threshold -> revise rubric and re-measure. The panel is not trusted until calibrated.
- **Execution seam** — reproducibility: same task + product + fixed env -> variance within expected band; metadata captured every run.
- **Task-Generation seam** — representativeness: generated bank matches the declared scenario mix and stays within the constitution.
- **Sink seam** — correctness of the gap-derivative computation; both exits actually deliver (a feature item reaches roadmap intake; a bug record reaches the Vio tracker).
- Prior art: none yet (greenfield) — the golden set itself becomes the prior art for future scoring.

## Out of Scope

- **Workstream B (Vio bug management)** — only lightweight capture + handoff; no bug status/priority/state flow lives here.
- **Workstream C (competitor intel tracking)** — social/changelog/blog/Discord/GitHub-release monitoring. Acknowledged as the event trigger for A, but its build is deferred.
- **Full automation** of generate -> run -> review -> board — deferred until the manual methodology is validated.
- **Scaling beyond the minimal slice** — more domains, more competitors, more runs come after Phase A proves the loop.
- **Running the system via Vio itself** — desirable long-term reframe, not a Phase A deliverable.

## Further Notes

- Known LLM-reviewer biases to defend against in the rubric: preference for longer answers, confident tone, same-family outputs. Dual review does not remove these — hence golden-set calibration.
- The "moving target" problem is reframed as an asset: tracking the derivative measures *who iterates faster*, which a snapshot cannot.
- **Phase A minimal slice:** scenario domain #1 (closed-source desktop app operation, e.g. WeChat/CapCut); competitors = Simular Sai (same-layer) + one cloud voice-of-market rep (Manus OR OpenAI Operator) + Claude computer-use (reproducible benchmark); 5 tasks x 3 competitors x 3 runs. Cross-layer comparisons tagged `cross-layer (not same-condition)`.
- **Open items still needing an owner/decision:** (1) optional second human for high-fidelity golden-set calibration at version events; (2) real scenario-mix ratios (pending telemetry/interviews — see constitution v0); (3) cloud rep choice: Manus vs OpenAI Operator.
