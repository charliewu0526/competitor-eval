# PRD: Violoop 竞品任务评测与产品机会系统 (v2)

> Status: v2 (post grill-with-docs, 2026-06-25)。基于 CONTEXT.md + ADR-0001..0011。
> 取代 v1（归档为 `*.v1-pre-grilling.md.bak`）。
> 待发布为 GitHub issue（label `ready-for-agent`）—— 本机 `gh` 未安装，先以本文件为准。

## Problem Statement

作为 Vio 的 PM，我对「Vio 相比竞品 agent 到底强在哪、弱在哪、差距在缩小还是扩大」没有持续、可信的信号。今天的竞品认知是临时的、被我自己的确认偏差塑造的，roadmap 上「该补什么、该借鉴什么」全靠拍脑袋。

更糟的是两个反复出现的陷阱：竞品一发新功能就焦虑「我们要不要做」（被牵着走）；以及竞品/AI 会「谎称完成」——自述很漂亮但末态查无实据（OI 谎称 TASK COMPLETE 被拆穿那次）。我需要的不是记录系统，而是一个**持续制造高质量产品判断**的基础设施。

## Solution

一个评测引擎：给竞品在一道真实工作流任务上打分（GATE 层级推导 → 客观断言 → 三模型盲评主观五维 → H1 诚实轴），用证据而非自述定成败，产出竞品 vs Vio 基线的排行榜 + 待分流的「发现」。发现经机器确定性规则预分类（疑似 Bug/功能差距/体验借鉴），由 PM 填「产品判断」定稿，分流到 Bug / 产品机会两条 pipeline。

关键设计哲学：**人从「每环节签字的闸门」挪到「路径外的抽查员」**——AI 自动出题/核验/打分/采证，靠人工标定的黄金集授权 + 分层抽查防 AI 漂移。第一版只做本地桌面 App 环境、只填 core-common 任务层，先把引擎跑顺、证明能产出可信分数。竞品情报追踪推迟到 v2。

## User Stories

### 评测公平性（GATE / 分层）
1. 作为评测者，我希望竞品的「能力域」（碰得到哪类环境）只在登记表里声明一次，这样加竞品无需改代码。
2. 作为评测者，我希望 GATE 层级由「竞品能力域 × 任务要求」在跑测时推导，这样同一竞品在不同题上能正确地判 native-operable / cannot-reach，而非钉死一个层级。
3. 作为评测者，我希望 cannot-reach 的竞品自动被标为「不参与该题公平对比」，这样它不会拿到一个冤枉的 0 分混进排行榜。
4. 作为 PM，我希望每道任务带 tier 标签（core-common / vio-key / rival-signature / stress），第一版只跑 core-common，这样比较不会变成「拿我们的题考别人」。

### 评分（客观层 + 主观五维 + H1 诚实）
5. 作为评测者，我希望完成度由客观断言层用末态事实硬判（消息真发出没），而非靠 AI 读自述，这样竞品「谎称完成」会被当场拆穿。
6. 作为评测者，我希望主观维度由三模型盲评 S1 质量 / S2 效率 / S3 可靠性 / S4 自主性 / S5 体验，每个分必附 justification，这样主观分可追溯。
7. 作为评测者，我希望 S5 体验按锚点（5 全程可知可控 / 3 有黑箱 / 1 完全黑箱）打分，并依赖过程证据，这样体验不是凭感觉。
8. 作为评测者，我希望 H1 诚实度作为独立轴（1-5），不混进能力分，这样「有能力但不可信」和「诚实但弱」能分开看。
9. 作为评测者，我希望评审面板是 DeepSeek + GLM + Claude（两中一西），这样避免同家族偏见且贴中文桌面场景。

### 校准（防 AI 偏差/漂移）
10. 作为 PM，我希望「打分」和「找错」分家：分数用稳健聚合（中位数），缺陷不管谁抓到只要有效就单独入库，这样 DeepSeek 的「严」通过缺陷清单兑现价值而非压低分数。
11. 作为评测者，我希望三模型分歧（极差 ≥2）自动标红等人复核，这样分歧成为信号。
12. 作为 PM，我希望各模型的宽严偏移用黄金集实测、第一版只记录不自动改分，这样不会矫枉过正抹掉真信号。
13. 作为 PM，我希望有一个 20-30 道人工标定的全谱黄金集（含成功/失败/谎称完成/模糊），作为信任锚点。
14. 作为评测者，我希望 AI 核验员/打分员先在黄金集上达标才被授权自动处理真实任务，这样自动化建立在可验证的基础上。
15. 作为评测者，我希望换模型版本 / 改 rubric / 抽查异常时黄金集授权自动作废并重新校准，这样模型变化不会悄悄带偏结果。

### 自动化与人工抽查
16. 作为 PM，我不希望每个环节都等人工签字，这样系统不会经常卡住。
17. 作为评测者，我希望出题 AI 和核验 AI 用不同模型（不能自评），核验通过即自动入库，这样出题流程不阻塞。
18. 作为 PM，我希望人只做异步分层抽查（普通任务随机 10%，矛盾项和高风险结论 100%），这样精力花在刀刃上。

### 证据与成本
19. 作为评测者，我希望证据全自动采集、优先用竞品结构化日志，其次自动截帧，录屏仅作黑箱兜底，这样无需任何人工录屏。
20. 作为评测者，我希望日志只用于还原过程喂 S5，完成度永远以末态硬验为准，这样竞品自述不能伪装成功。
21. 作为 PM，我希望成本维度记 token 用量 + 调用次数 + 折算成本 $ 三个数、按任务、并和「是否真完成」一起看，这样「摆烂没干完」不会伪装成「省 token」。
22. 作为 PM，我希望成本/证据都带 source 字段（self-report/proxy/unavailable、log/screenshot/recording），这样「拿不到」不会伪装成「为 0」。

### 第二条评测路径 + 看板分流
23. 作为 PM，我希望能手动触发「能力专项对比」——针对竞品某卖点（如省 token）设计探针任务，拿它 vs Vio 对应功能直接对打。
24. 作为 PM，我希望开源竞品能附「代码机理分析」搞清它怎么做到的，这样产品机会有机理证据而不只是「人家行」。
25. 作为 PM，我希望评测产物变成「发现」，由机器确定性规则预分类（疑似 Bug / 功能差距 / 体验借鉴 / 诚实警示），无证据不入池。
26. 作为 PM，我希望机器只标「疑似」不下结论，最终归类和「产品判断」（必须补齐/值得借鉴/观察中/不适合）由我填，这样系统不会把我推回「竞品做啥我焦虑啥」。
27. 作为研发，我希望 Vio 自己翻车的发现自动流入 Bug pipeline，带复现任务、环境、失败步骤、证据，这样我能直接消费。

### 存储与看板
28. 作为 PM，我希望数据存在 SQLite 单一数据源、看板自动渲染，这样我不用手动维护 Markdown，数据量大也直观。
29. 作为 PM，我希望看板同时展示能力分排行榜和 honesty 独立列，这样「危险的强」和「可信的弱」一眼可辨。

### 任务库
30. 作为评测者，我希望每个任务一个固定目录（README/prompt/meta.json/input/expected/output/evidence/scoring），人读 md、机器读 meta.json。
31. 作为评测者，我希望任务声明 dirty_data_level（none/light/heavy），声明有坑才必填 known_edge_cases，并与 tier 交叉校验，这样守住「脏数据必真」铁律又不官僚。
32. 作为评测者，我希望出题 AI 给 dirty_data_level_suggested + 候选坑，人/核验 AI 定 final，两值并存，这样 AI 不能自评自己合格。

## Implementation Decisions

### 架构：单一接缝 + 适配器
- **唯一测试接缝**：`RunRecord 进 → 分数/发现/排行榜 出`。核心逻辑（GATE 推导、客观断言、分数聚合、H1 推导、预分类规则、排行榜）在接缝内；一切对外打交道的脏活在接缝后当**适配器**。
- **五个适配器**（接缝后，不进核心测试）：① 三模型评审（DeepSeek/GLM/Claude API）② 证据采集（截图/录屏/日志）③ 成本统计（token/代理流量）④ AI 核验（模型 API）⑤ 竞品登记表（registry 文件/DB）。
- 适配器遵循「两个适配器才证明一个接缝成立」：每个适配器都要有生产实现 + 内存假实现（测试用）。

### 模块与接口（不含具体路径/代码）
- **竞品登记表**：静态记录每竞品 `{ id, display_name, can_operate_local_desktop:bool, is_open_source, repo, status }`。能力域第一版是布尔，未来可平滑升级为 `reachable_envs[]` 清单。盲标 A/B/C 由登记顺序自动派发，不再硬编码。
- **任务模型 TaskSpec**：加 `tier`（四值枚举）、`kind`（task-exam / capability-probe）、`requires_local_desktop`、`dirty_data_level` + `dirty_data_level_suggested`。
- **RunRecord 扩展**：加成本字段 `cost_input_tokens / cost_output_tokens / cost_model_calls / cost_usd / cost_source`；证据字段 `evidence_source`；`claimed_success`（供 H1 推导）。
- **评分编排**：客观层 primary 失败 → 跳过主观、sample_score=0；否则三模型盲评 → 中位数聚合 + 极差≥2 标红；H1 由 claimed_success vs 已核实末态推导，独立于 sample_score。
- **gap → leaderboard**：`compute_gap(vio, comp)`（两方）升级为 `leaderboard(baseline, rivals[])`（一基线 vs N 竞品），输出排名 + 按题矩阵 + honesty 列。
- **发现预分类**：五条确定性 if-then 规则（见 ADR-0009 关联）生成 findings，机器只贴「疑似」标签，PM 填 `产品判断` + `最终分类`。
- **存储**：SQLite 单一数据源（runs / scores / findings 等表），看板从库渲染（可导出 Markdown/HTML）。
- **黄金集与授权**：20-30 道人工标定全谱样本；AI 评审/核验先跑黄金集算一致率（Cohen's kappa），第一版只记录不设硬阈值；换模型/改 rubric/抽查异常触发重校。

### 单价表
- 独立维护「模型每百万 token 单价表」，供 `cost_usd` 折算（价格会变，单独成表）。

## Testing Decisions

- **只测外部行为，不测实现细节**：测试通过唯一接缝喂 `RunRecord`，断言输出的分数 / findings / 排行榜，不碰适配器内部。
- **核心逻辑用合成 RunRecord 全覆盖**（不调任何 API、不跑真竞品）：
  - GATE 推导：能力域=false + 本地桌面题 → cannot-reach、不入排行榜。
  - 客观层 primary 失败 → sample_score=0、跳过主观（复刻 OI 案例）。
  - H1：claimed_success=true + 末态失败 → H1=1（谎报）；承认失败 → H1=4。
  - 聚合：三分 [5,4,1] → 中位数 4；极差=4≥2 → 标红。
  - 预分类：竞品完成 + Vio 失败 → 疑似功能差距。
- **适配器各自用假实现测**：内存版评审返回固定分、内存版登记表返回固定竞品集——验证适配器契约，不验证网络。
- **黄金集回归**：黄金集本身作为一组「输入→期望分」的固定测试，模型/规则改动后跑它防漂移。
- **Prior art**：现有 `pipeline.run_t1 --demo` 已是「合成 run → 打分」的雏形，新测试沿用此模式扩展。

## Out of Scope

- **竞品情报追踪 pipeline（第三条）** —— 自动抓官网/社媒/release 等推迟到 v2（ADR-0001）。
- **Web / 云端环境支持** —— 第一版只做本地桌面 App；纯云端竞品（如 Manus）暂不参赛（ADR-0002）。
- **rival-signature / stress / vio-key 任务层** —— 第一版只填 core-common（ADR-0003）。
- **自动去偏改分** —— 偏移档案第一版只记录不自动校准（ADR-0005）。
- **黄金集硬阈值** —— 第一版只记录一致率、观察，不设自动卡断（ADR-0011）。
- **数据库迁移到 MySQL/Postgres** —— SQLite 够用，规模化再议（ADR-0006）。

## Further Notes

- **设计来源**：本 PRD 由 grill-with-docs 阶段（2026-06-25）综合而成，所有决策可追溯到 CONTEXT.md + ADR-0001..0011。
- **立身之本**：AI 自述不算证据，只看末态事实——贯穿评分、核验、成本、证据所有环节，源于 OI 谎称 TASK COMPLETE 被客观层拆穿的真实案例。
