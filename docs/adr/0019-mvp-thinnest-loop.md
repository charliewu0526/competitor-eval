# 第一版切最薄闭环,先验证「实习生模式」成不成立

grill 定的九条加起来是好几个月的工程(上服务器、鉴权、文件上传、脱敏流水线、三级权限、版本保鲜……)。一次性全做 = 迟迟上不了线,而「实习生模式」本身有个未验证的假设:新人跑竞品能否产出可用数据(执行偏差残余风险,ADR-0015)——这只有真有人用了才知道。

决定第一版只做**最薄的能转起来的闭环**:实习生注册 → 领任务(Assignment)→ 提交交付物+执行日志包 → 数据进现有评测引擎 → 出能力域榜单。刻意砍到人工代替的:①脱敏(先人工洗日志再送审,不做自动脱敏流水线)②方法复核闸(先口头/线下把关,不做系统闸)③自动 stale 判定(先人看测试日期,不做后台自动标灰)。目标:两三周内让 1-2 个实习生真跑一道对比任务,验证模式成立,再拿真实使用逼出剩余八条的优先级。呼应立身之本「先搭框架机制,再填内容深度」。

## 代价

MVP 上线时脱敏靠人工 = 有洗漏破盲的风险(可接受,量小);方法导出无系统门禁 = 靠自觉(可接受,人少)。这些「人工代替」项必须显式登记为技术债,不能因为「先跑起来了」就忘记补。若模式验证失败(实习生数据不可用),及时止损,不硬推完整系统。

## 技术债还账进度(2026-07-29 复核实际实现后更正)

三条「人工代替」债实际交付时已随 MR 系列还清,本 ADR 更正登记以免误导:

- **①脱敏 —— 已还(自动化)。** 原计划「人工洗日志」,但 MR-9(#45 日志 raw/redacted 双视图)+ MR-10(#46 盲评面板)已把送审前脱敏做成**全自动**:`blind_panel.run_blind_panel` 送面板前必调 `logview.make_redactor` 洗品牌/模型指纹,词典 DERIVED(品牌来自 registry、模型来自价表),加竞品/加模型不改脱敏代码。破盲守卫测试 `test_blind_panel_mr10.PanelSeesRedacted` 锁死「指纹绝不进面板 prompt」。无人工洗日志环节。
- **②方法复核闸 —— 已还(系统门禁)。** MR-14(#50)`pipeline/methods.py` 实现 draft→approved→exported 系统级状态机门禁,未经 reviewer/PM 把关不能导出给研发。非「口头/线下」。
- **③自动 stale —— 已还(自动派生)。** MR-12(#48)`domain_board.is_stale` 按 tested_at 超新鲜度窗口(默认 90 天)**自动派生** stale,榜单渲染即标灰。非「人看日期」。tested_at 缺失时不擅判新鲜,如实沿用已知标志。

H-1 连接生命周期(体检高危项)亦已于 2026-07-29 还清(threading.local 按线程复用连接)。至此 ADR-0019 登记的人工代替债全部还清。
