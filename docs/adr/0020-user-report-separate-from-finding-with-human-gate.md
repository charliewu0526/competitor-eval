# 用户反馈是独立于 Finding 的第二条流,且 AI 修复必经人工闸门

系统要加「用户报 bug → AI 辅助修复」功能。目标是减轻 owner 逐个 bug 过手的负担,不是全自动化。

**决定一:User Report 是全新独立实体,不复用 Finding。** Finding 是评测引擎自动长出来的、喂产品判断的证据链(机器只标现象不下结论、无证据不入池、过出厂安检);User Report 是登录用户主动报的、喂「修 bug」的工程缺陷流。二者判定标准、生命周期、消费者都不同。硬塞进 Finding 会污染那条辛苦建立的可信证据链。两条流并行不混,看板(Finding 池)与反馈台(Report Console)各自独立。

**决定二:AI 只起草补丁,人工一键闸门在环内(B 档,非端到端全自动 C 档)。** owner 的真实痛点是「从零调查每个 bug」,不是「敲修复代码」。B 把 owner 降为「审一份现成 diff+测试结果」,工作量真降;同时堵死 C 的两个致命面:①公网可达系统 + 不可信输入直接驱动有写权限的 agent = prompt-injection→RCE;②坏补丁自动上线 = 全员宕机而只有 owner 能救。

## Considered Options

- 复用 Finding 加 source 字段 —— 拒。污染证据链,两种流生命周期不同,字段互相打架。
- 端到端实时自动修复(改码→自动合并→自动部署)—— 拒。当前是单机+公网 tunnel,无鉴权缓冲、无金丝雀、无回滚,是把安全洞焊进生产。留到 v2 且需前置条件齐备。
