# 从单机引擎搬成多人 Web 服务

现引擎是单机的:本地 SQLite、跑在 PM 机器上、靠 computer-use 操作,对「一个人跑」够用。但多人系统每条需求都在假设一个部署形态:实习生自注册登录(需在线账号系统)、上传交付物+日志包(需服务器接收+存储)、领任务防两人领同一个(需并发控制的中央库)、多角色权限(需会话鉴权)。这些无法在单机本地文件上成立。

决定:把单机引擎**搬成部署在服务器上的 Web 服务**,数据库从本地 SQLite 迁到支持多人并发的形态。这不改变前八题定的任何逻辑(评分哲学、盲评、角色、保鲜全不变),只决定系统「活在哪、怎么被访问」。选正统路(而非半上云同步/内网多账号),因为「自注册链接私发」「防并发领取」「文件上传」都要求一个真正的在线服务端。

## 代价

工程量最大的一条:要定部署方式、并发数据库选型(SQLite → Postgres 或托管库)、文件/日志包对象存储、鉴权会话、脱敏流水线在服务端的位置。是唯一带持续运维 + 成本的决策。评分引擎本身(pipeline/)可基本复用,主要新增的是其外围的服务层 + 存储层 + 前台。数据库选型、文件存储方案留待 to-prd/to-issues 阶段定。
